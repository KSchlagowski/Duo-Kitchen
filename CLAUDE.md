# Rules for AI

## Hard rules

- **Supabase RLS**: every new table must enable RLS with granular per-operation, per-role policies. Migrations go in `supabase/migrations/` named `YYYYMMDDHHmmss_short_description.sql`.
- **Household-scoped tables**: every household-owned table (not the public recipe/product library — see **Public library tables** below) has `household_id uuid not null references public.households on delete cascade` (indexed) and per-operation RLS policies `to authenticated` with `using` / `with check (household_id in (select private.user_household_ids()))`. No `anon` policies. Never query `household_members` directly inside a policy — always go through `private.user_household_ids()`. Extend the isolation test (`supabase/tests/household_isolation.sql`) for each new table. Its classification catch-all fails on any `public` table that has no `household_id`, is not `households`, and is not in its `library_tables` array — so every new `public` table is either household-scoped or deliberately added to that array as a library table. CI runs that test against the already-deployed schema, not the branch's migrations — so before merging any migration, run `npx supabase db push` and then `npm run test:rls`.
- **Secrets**: `SUPABASE_URL` / `SUPABASE_KEY` are server-only — read them via `astro:env/server` (declared in `astro.config.mjs` `env.schema`), never `import.meta.env` in client code. Local Cloudflare secrets go in `.dev.vars` (gitignored).
- **Supabase is cloud-only**: always work against the hosted Supabase project, ref `tvmfkhnxxsnmvogplknz` (`SUPABASE_URL=https://tvmfkhnxxsnmvogplknz.supabase.co`; link with `npx supabase link --project-ref tvmfkhnxxsnmvogplknz`). Do not run a local Supabase stack — no `npx supabase start` / `stop` / `db reset`, no Docker. Apply migrations to the cloud project with `npx supabase db push`; run SQL with `npx supabase db query --linked`. This applies to CI too.
- **Client-callable Postgres functions live in `public`**: the `private` schema is deliberately not API-exposed, so a definer helper there is unreachable as an RPC endpoint — `private` is for internals only (`private.user_household_ids()`, the sign-up trigger). Anything a client calls through `supabase.rpc(...)` must be `create function public.<name>` with `security definer`, `set search_path = ''`, **every** name fully qualified (`public.household_members`, `auth.uid()`), followed by `revoke execute on function … from public, anon;` then `grant execute on function … to authenticated;`. The revoke is mandatory, not cosmetic: Supabase's default privileges grant `execute` on new `public` functions to `anon`. Validation errors are raised with distinct SQLSTATEs in class `KD` (see `supabase/migrations/20261007120200_household_invites.sql`), never a bare `P0001`, so tests can assert the precise reason and the UI can map each to its own message. The isolation catch-all inspects **tables only**, so every new function's grants need their own assertion.
- **Write-revoked tables**: `households`, `household_members` and `household_invites` are read-only for clients — all writes go through security-definer functions. `household_invites` nonetheless carries all four per-operation policies, because the catch-all in `supabase/tests/household_isolation.sql` reads `pg_policies` and would reject the table without them; the `revoke insert, update, delete, truncate … from authenticated` is what actually makes three of those policies unreachable. **Policies and grants are independent levers, and both halves are load-bearing — do not "simplify" by dropping either.** The isolation test asserts the revokes directly so this cannot be undone silently. `meal_plans`, `plan_dishes` and `plan_meals` (S-03) follow the same pattern: writes only via `public.save_meal_plan`, and their revoke list includes `maintain`.
- **Public library tables** (F-04, `supabase/migrations/20261008150000_shared_recipe_library.sql`): `products`, `recipes`, `recipe_components`, `recipe_ingredients` and `recipe_steps` are one library shared by every **authenticated** user (never `anon`) and have **no** `household_id`. Each carries exactly one `select … to authenticated using (true)` policy and no write policies; `insert, update, delete, truncate, references, trigger` are revoked from `authenticated` and `all` from `anon`. Both levers are load-bearing (a recreated `public` table gets Supabase's default grants back) and the isolation test asserts both. A household-owned or per-person row may reference a library row with a plain FK — never the reverse. Future write rule (lands with S-07, which adds a nullable `created_by`): seed rows (`created_by is null`) stay immutable to clients; user-added rows are editable by their author and the author's current household partner, resolved through a definer helper (never `household_members` in a policy). The `5eed000N-…` id namespace is reserved for migrations: no library write path may accept a client-supplied `id` — use a definer RPC or a column-level `grant insert (<cols without id>)` — and S-07 adds `created_by` together with `check (created_by is null or id::text not like '5eed%')`. S-07 must **replace** the isolation test's "every library policy is SELECT-only" catch-all assertion with one requiring each write policy to reference `created_by` and a definer helper; it must not simply delete it.
- **Tailwind class merging**: use the `cn()` helper from `@/lib/utils` for conditional/merged class names. Do not concatenate class strings manually.

## Commands

Scripts: @package.json. Project-specific notes:

- `npm run smoke` — dependency-free auth-flow smoke test (`scripts/smoke.mjs`) against a running server, `BASE_URL` env (default `http://localhost:4321`). Run after dependency upgrades; CI runs it against the production preview backed by the hosted Supabase project.
- `npm run test:rls` — household isolation test (`supabase/tests/household_isolation.sql`) against the hosted Supabase project (`--linked`); runs in a rolled-back transaction so it commits nothing, fails with a descriptive error on any broken assertion. CI runs it in the smoke job.
- `npm run test:seed` — seed integrity test (`supabase/tests/seed_integrity.sql`) against the hosted project (`--linked`), rolled back: seed content covers every solver rule (rounding steps, pieces, raw/cooked, division modes, step timings, meal types, aisles, macro levers) and the seed rows of the public library (the `5eed000N-…` ids) are internally consistent, depend only on other seed rows and match pinned per-table counts. Run it after every seed content migration (which updates those counts); CI runs it in the smoke job.
- Pre-commit hooks: husky + lint-staged runs `eslint --fix` on `*.{ts,tsx,astro}` and `prettier --write` on `*.{json,css,md}`.

## Architecture

**Astro 7 SSR app** (`output: "server"`) with React 19 islands, Tailwind 4, Supabase auth, and shadcn/ui components. Deployed to Cloudflare Workers.

### Auth flow

- `src/lib/supabase.ts` — creates a Supabase SSR client using `@supabase/ssr` with cookie-based sessions.
- `src/middleware.ts` — runs on every request, resolves the current user, attaches to `context.locals.user`. Redirects unauthenticated users away from routes listed in `PROTECTED_ROUTES`.
- API endpoints: `src/pages/api/auth/{signin,signup,signout}.ts`
- Auth pages: `src/pages/auth/{signin,signup,confirm-email}.astro`
- Protected page example: `src/pages/dashboard.astro`
- Invite / redemption (S-01): `src/pages/api/household/{invite,redeem}.ts`, the unprotected `src/pages/join.astro`, and `src/lib/services/invites.ts` (the single home for both RPC calls and for mapping the `KD0xx` SQLSTATEs to user-facing messages). `/join` is intentionally **not** in `PROTECTED_ROUTES`: besides sign-in and sign-up it is the one page an unauthenticated visitor may reach. It stores the code in an `httpOnly` `dk_invite` cookie (`src/lib/invite-cookie.ts`, 7 days, matching the invite TTL, `sameSite: "lax"` because the link is followed from an email client), which is what carries the code across the sign-up → confirm-email → sign-in detour; `/api/auth/signin` redirects to `/join` instead of `/` while that cookie is present. Redemption is a deliberate **POST**, never a one-click GET, because no application path can undo it.
- Households: `public.households` / `public.household_members` (one household per account, enforced by `household_members.user_id unique`); the sign-up trigger `private.handle_new_user()` creates a household of one for every new account. Clients cannot write these tables directly. Linking a partner is therefore an **update** of one membership row, done by `public.redeem_household_invite()`; the old household is left intact and memberless and recorded in `household_invites.redeemed_from_household_id`, which the README cleanup query relies on to spare it. There is no leave/unlink path, so a redemption needs `postgres` to undo. Redemption never inspects household content: KD006 (the old "non-seed rows would be left behind" guard) is retired with F-04 and must not be reused.
- Per-person data (macro targets, ratings — S-02 onward) belongs to the user, not the household: it must be keyed on `user_id` and scoped by `household_id` for RLS, so it travels with the person through a redemption and stays visible to the partner (PRD §Access Control). `user_id` is the key or the leading part of it — `macro_targets` is one row per person (PK `user_id`); `recipe_ratings` (S-06) is one row per person per recipe (PK `(user_id, recipe_id)`, plain FK `recipe_id → public.recipes`). That plain FK is only valid because recipes are a public library (F-04) — a per-person row must never reference a household-owned row, since the membership cascade would move it to a household the referenced row is not in. Per-person tables carry `user_id` in the key plus a composite FK `(household_id, user_id) → public.household_members (household_id, user_id) on update cascade on delete cascade` (alongside the plain `household_id` FK the hard rule requires). That FK is what makes the rows travel through `redeem_household_invite()` — referential actions run as the table owner, outside RLS — so never add a per-table move step to the function. Membership moves must stay a single `update … set household_id` of the `household_members` row; deleting and re-inserting a membership cascades away every per-person row for that user. Write policies (insert/update/delete) add `and user_id = (select auth.uid())` to the helper predicate, so the partner can read but not write; the isolation catch-all does not check that owner predicate, so each table needs its own strict `insufficient_privilege` insert probes. `macro_targets` (`supabase/migrations/20261008120000_macro_targets.sql`) is the first such table.
- Macro targets (S-02): the protected `src/pages/targets.astro` (your own targets as a form, your partner's read-only), `POST /api/targets` (`src/pages/api/targets.ts`, zod with a digits-only regex **before** number conversion so a blank field can never coerce to `0`), and `src/lib/services/macro-targets.ts` (reads, the upsert, `formatMacroTargets()` — whose output the smoke test matches — and the soft kcal-mismatch hint). The dashboard shows a `Targets:` summary line.
- Meal plans (S-03, `supabase/migrations/20261008170000_meal_plans.sql`): household-scoped and write-revoked. `meal_plans` holds one row per household per `start_date` (3 consecutive days). `plan_dishes` holds one cooked batch of one library recipe. `plan_meals` holds one filled slot (`day_index` 0–2 × `meal_type`) that eats from a dish. Empty slots are absent rows. `eater_user_id` is null for "both", otherwise one member's id (`auth.users on delete set null`). `plan_meals_dish_id_key` (one meal per dish) is S-03-only: S-08 drops it so one dish can cover several days, with no data migration. The only write path is `public.save_meal_plan(p_start_date, p_meals jsonb)`. It applies a slot-level diff, so unchanged slots keep their ids. It raises KD010 (malformed payload), KD011 (unknown recipe), KD012 (eater not in the household) and reuses KD007. **Never give plan rows the per-person composite `(household_id, user_id) → household_members` FK**: plans are household-owned and stay behind in the origin household on redemption, and that FK's cascade would fail the redemption with 23503. The eater's membership is checked by the RPC instead. App: the protected `src/pages/plan.astro` (form grid, no island), `POST /api/plan` (`src/pages/api/plan.ts`), `src/lib/services/meal-plans.ts` (reads, the RPC call, the KD → message map, `formatPlanSummary()`, which the smoke test matches) and, for the recipe picker, S-05's `getRecipeCards()` in `src/lib/services/recipes.ts` (S-03's own `listRecipes()` / `RecipeListItem` were folded into it when S-05 rebased onto S-03; meal-type labels come from `src/lib/recipe-labels.ts`). The dashboard shows a `Plan:` summary line.
- Recipe library browsing (S-05): the protected `src/pages/recipes/index.astro` (card grid, `src/components/recipes/RecipeCard.astro`) and `src/pages/recipes/[id].astro` (full detail; the id is checked with `z.guid()` (any hex id Postgres accepts, not only RFC-versioned ones) before any query, so a malformed or unknown id is 404 and a failed read is 500 — never "not found"). Reads are `getRecipeCards()` / `getRecipeDetail()` in `src/lib/services/recipes.ts`, `getRecipeCards()` also feeds S-03's plan picker. `getRecipeDetail()` runs **three flat queries** (recipe, components with nested ingredients and products, steps) instead of one nested embed, because `recipe_steps` has FKs to both `recipes` and `recipe_components` and embedding both under `recipes` risks PostgREST's PGRST201 ambiguity. The per-100 g arithmetic and the display strings the smoke test pins (`formatMacroTotals()`, `formatCookedLine()`) live in `src/lib/services/recipe-macros.ts` (pure, no Supabase — S-04's solver reuses it); every enum label lives in `src/lib/recipe-labels.ts`, the single map S-14 localises. Macros are for one whole base batch; the per-person split is S-04's. **No photo column**: this revises F-02's note that S-05 would add `photo_url` — cards show a deterministic placeholder and `RecipeCard.photoUrl` is always `null`; the column (nullable, keeping the library revokes and the select-only policy) and its Storage policy land with the first slice that can supply a photo (S-07's write path or S-12). Ratings seam for S-06: `RecipeCard.astro` has a named `ratings` slot that renders nothing until filled; S-05 stores and shows no ratings.
- Products and recipes (`products`, `recipes`, `recipe_components`, `recipe_ingredients`, `recipe_steps`) are **one public library** (F-04, see the **Public library tables** hard rule): one canonical set of rows, not linked to any household, read-only for clients. Signing up creates a household and a membership only — no library rows. Child tables use plain FKs (`recipe_steps (component_id, recipe_id) → recipe_components (id, recipe_id) on delete set null (component_id)` keeps a step's component in the same recipe; `recipe_ingredients.product_id` is `on delete restrict`). Seed rows keep their stable `5eed000N-…` ids (N = 1 products, 2 recipes, 3 components, 4 ingredients, 5 steps), which tests use to tell seed rows from user rows. Seed content changes are plain `insert` / `update` statements on the public tables in a new data-only migration — there is no per-household fan-out and no `private` template set any more.
- Ownership classes: households own only what is theirs (plans, shopping lists); people own their targets and ratings; recipes and products belong to nobody. S-03, S-05, S-06 and S-07 reference `public.recipes` / `public.products` directly.

### Key conventions

- **Astro vs React**: use a `.tsx` island only if the component uses state, effects, or browser event handlers; hydrate with the narrowest `client:*` directive (prefer `client:visible`/`client:idle` over `client:load`). Everything else is `.astro`.
- **shadcn/ui**: components live in `src/components/ui/`, "new-york" style variant. Install new ones with `npx shadcn@latest add [name]`.
- **API routes**: use uppercase `GET`, `POST` exports; validate input with zod.
- **React**: no Next.js directives ("use client" etc.). Extract hooks to `src/components/hooks/`.
- **Services/helpers**: any Supabase query or domain logic used by more than one page or API route goes in `src/lib/services/`. Pages and API routes must not call `supabase.from(...)` directly. Generic helpers go in `src/lib/`.
- **Shared types** (entities, DTOs) go in `src/types.ts`.
